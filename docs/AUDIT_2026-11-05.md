## 2. Defects found by this audit

Severity follows the project style: **P0** = wrong or destructive behaviour, fix before
the next flash; **P1** = user-visible or durability problem; **P2** = quality gap.

### P0-1 — Settings and calibration share one flash page, and destroy each other

* `app/flash_store.h:7` `FLASH_STORE_ADDR = 0x0800F800` (calibration)
* `app/flash_store.h:12` `SETTINGS_ADDR = 0x0800F900` (settings)
* `app/flash_store.c` erases a full page (`FLASH->AR = addr`, PER, STRT) before writing.
* The STM32F103C8 page is **1 KiB**, so `0x0800F900` lies 256 bytes inside the
  `0x0800F800` page.

Consequence: every `settings_save()` erases the calibration record, and every
`cal_store_write()` erases the settings record. Both are called from the menu, so the
instrument silently loses its calibration as soon as the user changes a setting, and
loses its settings as soon as the user touches the calibration pages.

The linker script compounds this: `SETTINGS ORIGIN = 0x0800F800, LENGTH = 4K` runs to
`0x080107FF` — 2 KiB past the end of a 64 KiB part — while the real separate pages
`0x0800F000` and `0x0800F400` are covered by no region at all.

Fix (planned, not yet applied): emit `.settings` at `ORIGIN = 0x0800F000, LENGTH = 4K`;
put `SETTINGS_ADDR` at `0x0800F400`; keep calibration at `0x0800F800`; never touch
`0x0800FC00` (vendor device record). Add a test that asserts the two addresses are in
different 1 KiB pages.

### P0-2 — Calibrated Vpp readout mixes millivolts with ADC counts

`app/main.c:466-483`:

```c
vpp_uv = cal_raw_to_uv(max) - cal_raw_to_uv(min);
vpp_mv = vpp_uv / 1000;
div10  = (vpp_mv * 80) / s_span;      /* s_span is counts across 8 div */
```

`s_span` is an ADC-count span (`8 * mv * 4095 / 3300`, clamped 16..4095), not
millivolts. With the identity calibration (1 count = 1 µV) a full-scale 4095-count
signal produces `vpp_mv = 4`, so the panel rounds to **`Vpp 0.0d` permanently**; with a
realistic calibration the result is also wrong by the scale factor between counts and
mV. The preceding implementation (`stats.vpp * 80 / s_span`) was dimensionally correct.

Fix: either keep the count ratio (`stats.vpp * 80 / s_span`) or take the calibrated mV
and divide by the switch-derived mV/div (`vpp_mv * 10 / s_mv`), with a zero guard.

### P0-3 — The trigger level can only increase, and the default can never trigger

`app/menu.c:144`:

```c
if (m->trigger_level < 4095) m->trigger_level += 64;
acq_set_trigger_level(m->trigger_level);
```

There is no decrement and no way to get back below the current value except resetting the
instrument. The default is `ACQ_TRIGGER_LEVEL = 2048`, while the front end idles near
1195 counts, so in NORM the level sits above the signal and the scope appears dead until
the level can be lowered — which the menu cannot do.

Fix: a two-direction control (short step up, long step down, or a mode row that
selects direction), and clamp to a safe band (the AWD needs headroom for hysteresis).

### P1-1 — Menu long-hold bounces and cannot close cleanly

`app/menu.c:109` on a >1500 ms hold does `state = depth-1; button_down = 0;` while the
button is still held. The next poll sees a fresh press edge and advances **deeper**
again, so holding the button walks the menu down one level and straight back up. On the
root page (`MENU_NONE`) the same edge advances to page 1.

Also `menu_render()` paints rows 20..39, which are inside the plot area (grid starts at
y=16). Each new frame clears the plot and the menu is redrawn after the frame, so the
menu flickers at the frame rate; in HOLD (`s_run == 0`) no frame is drawn, and closing
the menu leaves its text on screen until the next RUN frame.

### P1-2 — The superloop runs at 2 Hz when not streaming

`app/main.c:787`: `HAL_Delay(s_stream ? 0 : 500)`. Non-streaming behaviour:

* acquisition ~2 frames/s (a scope should be 15–30 fps);
* menu polled every 500 ms, so any press shorter than 500 ms can be missed entirely;
* PC-link command/reply latency up to 500 ms;
* hold-to-adjust needs several 500 ms polls, making the menu feel broken.

The delay is bounded (N-03 is satisfied) but far too coarse. A tick-based scheduler
(1–5 ms) or at least `HAL_Delay(20)` with the menu polled every pass is needed.

### P1-3 — Timebase label is hardcoded; trigger marker ignores the live level

* `app/main.c:441` formats the bottom-left label as `%lumV/d %ums/d` with a literal
  `1U`, so the timebase always reads **`1 ms/d`** whatever the user selected.
  `timebase_label()` already exists and is host-tested.
* `app/main.c:408` draws the trigger marker at `ACQ_TRIGGER_LEVEL` (2048) instead of the
  live `s_menu.trigger_level`, so the marker never moves when the level is adjusted.

### P1-4 — Persistence has no integrity or journal

* `settings.c` stores only magic (`'STA1'`, 12-byte record); no version, CRC, sequence
  or double-buffer. A torn or corrupt record silently degrades to defaults, and loaded
  values are not range-checked (timebase/mode are checked at apply time, level is not).
* `cal_store.c` stores only magic (`'CAL2'`); no CRC/version/journal. A corrupted
  record is used as-is if the magic happens to survive.
* Every menu step performs a full page erase + program. At two steps per second this is
  thousands of erase cycles per menu session and a ~10 ms CPU stall per step — flash
  endurance is ~10 k cycles per page. The page collision in P0-1 makes it worse.

Recommended: version + CRC + a two-slot (A/B) journal, save on release/idle rather than
per step, and return/act on `settings_save()`/`cal_store_write()` failures (currently
the menu ignores both return values — N-08 "honest failure" is not met here).

### P1-5 — The five fastest timebases are advertised but not achievable

`timebase.c` entries 0–4 (1, 2, 5, 10, 20 µs/div) are flagged `single_shot = 0`
(REPT-only) because their TIM3 tick (31–625 ns/sample) is shorter than the ADC
conversion time (~1.3 µs at 1.5 cycles). The table and tests know this; `acq.c` and
`main.c` do not consult the flag and accept all 27 indices, so selecting 1 µs/div
produces aliased data. Index 5 (50 µs/div) is the first physically usable single-shot
rate. Either hide/disable indices 0–4 in the UI and link, or implement equivalent-time
sampling.

### P1-6 — Stock feature parity: the product layer is still missing

The stock UI exposes, and the custom firmware does not:

| Stock feature | Ours | Notes |
|---|---|---|
| Vpp / Vrms / Freq / Duty readouts | Vpp only, and broken (P0-2) | RMS already computed in `measure.c`; frequency/duty need edge timing |
| `AV+` / `AV-` / `Cycle` / `All Disp.` | absent | averaging / display modes |
| `Save WF` / `Load WF` | absent | requirement F-07 |
| `Clr Offset` / `Default` / `Default restored` | absent | CAL-05; menu only increments |
| `Set CPL (SW1) to …` prompt | absent (and unobservable — see §3) | stock prompts the user to move the switch |
| `Running` / `Stopped` | implicit only (no label) | link RUN/STOP works |
| `Board info:` / `CFW: 113-18301-070` | diag screen shows build identity | not user-reachable |
| `Display1` / `Display2` | n/a | stock display variants |
| 9-step per-sensitivity calibration | single global offset/gain pair | CAL-03/CAL-04 |

These are **capability gaps, not hardware ceilings** (except coupling). Flash budget is
34 % used, so there is room: roughly 40 KiB flash and 11 KiB RAM remain.

### P2-1 — Rendering quality

`scope_draw()` clears the full plot and redraws the whole grid every frame; at 2 Hz this
is visible flicker and it also erases the menu (P1-1). A dirty-rectangle or
previous-trace erase (the trace buffer already exists) would fix both.

### P2-2 — Test coverage gaps

21 host suites cover the pure modules well, but these modules have **no host tests**:

`acq.c` (engine/HAL), `cal_store.c`, `flash_store.c`, `menu.c` (state machine),
`input.c`, `status.c`, `board_iwdg.c`, `board_uart.c`, `tim3_hw.c`, `stm32f1xx_it.c`,
`main.c` (wiring).

In particular there is no test for the two properties this audit found broken:
settings/calibration page separation, and menu long-hold direction. Host tests are
possible for the menu (inject a fake tick/button) and for the persistence layout
(address arithmetic), and should be added with the fixes.

### P2-3 — Link gaps

`SET_SPAN` is ineffective on the target because `ladder_refresh()` overwrites `s_span`
every frame (streaming skips both). There is no command to read measurements, the
trigger level, the calibration or the settings, and no error reply beyond the status
word. This is acceptable for v1 but should be documented as such.

## 3. Hardware limits (not fixable in firmware)

* **Coupling (AC/DC/GND)** is purely analogue: no ADC channel or GPIO observes it. The
  firmware can only label it "set by switch"; the stock `Set CPL` prompt is impossible
  to honour automatically.
* The ADC **injected group** does not convert on this clone (JEOC sets, JDR reads 0),
  which is why the ladder is read through the regular group during `acq_pause()`.
* PA8 as the menu button is a strong candidate (the vendor reads `GPIOA->IDR` bit 8 at
  boot) but is not proven on this unit; the encoder pinout is unknown.

## 6. Where the project stands, and what is left

**Verdict:** a working scope core with unusually strong verification, not yet a
product. Display, acquisition, front-panel decode, trace and the PC link are real and
bench-verified. Phases 1–5 added the missing control layer (snapshot integrity, trigger
modes, settings, calibration menu) but are host-only so far, and this audit found three
P0s that would make a flash of the current tree disappointing: lost calibration
settings, a permanently-zero Vpp readout, and a trigger level that cannot be lowered.

Remaining work, in order:

1. **Fix P0-1** (flash layout: `.settings` page at `0x0800F000`, `SETTINGS_ADDR` at
   `0x0800F400`, cal at `0x0800F800`, FC00 untouched) + host test for page separation.
2. **Fix P0-2** (Vpp dimensions) and **P0-3** (bidirectional trigger level, sane default).
3. **Fix P1-1/P1-2** (menu state machine + a real tick; acquisition ≥ 15 fps) and
   **P1-3** (timebase label from `timebase_label()`, live trigger marker).
4. **Fix P1-4** (settings/cal CRC + version + A/B journal; save on release; check
   return values) and add `cal_store`/`settings` host tests.
5. **P1-5**: disable the five fastest timebases in the UI/link until ETS exists.
6. **Product parity** (P1-6): Vrms/frequency/duty readouts, save/load waveform,
   average/cycle mode, clear-offset/defaults, per-sensitivity offset table
   (CAL-03/04/05).
7. **Bench validation** of Phases 1–5 and of every fix above (nothing has been flashed
   since the last verified image).
8. **P2**: dirty-rectangle rendering, link measurement/settings queries, encoder support
   if the hardware is confirmed.

Budget allows the whole list: ~40 KiB flash and ~11 KiB RAM remain, and the pure modules
that would carry the measurement/averaging work are already host-tested.

## 8. Remediation applied (2026-11-05, later)

All three P0 defects and the practical P1 defects were fixed in source; the image was
rebuilt and re-verified.

* **P0-1 flash layout** - settings now use two independent 1 KiB slots at
  `0x0800F000` and `0x0800F400`; calibration stays at `0x0800F800`; the vendor record
  at `0x0800FC00` is never written. The linker `SETTINGS` region starts at
  `0x0800F000` (4 KiB). Each settings record is 16 bytes with magic, version, sequence
  number and CRC-16/CCITT-FALSE; saves alternate slots, so the previous valid record
  always survives. Calibration uses the same 16-byte CRC record. `tests/test_flash_layout.c`
  pins page alignment/non-overlap; `tests/test_crc16.c` pins the CRC parameters.
* **P0-2 Vpp units** - `scope_draw()` now reports `stats.vpp * 80 / s_span`, a pure
  count ratio across the 8 displayed divisions; it matches the trace and cannot be
  zeroed by the identity calibration.
* **P0-3 trigger level** - the menu steps the level in both directions
  (+/-64, clamped 0..4095), and `main` applies persisted levels including 0. The
  default 2048 can now be lowered to the ~1195 idle front end.
* **P1-1 menu** - PA8 is sampled in `SysTick_Handler` at 1 kHz with 20 ms debounce;
  taps, double-taps (one step back) and long-holds (next page) are queued to the main
  loop, so short presses are no longer lost. The menu is drawn in the previously unused
  strip at y=214 (below the plot and the scale line), clears itself when closed, and
  auto-closes after 20 s idle.
* **P1-2 loop rate** - the non-streaming `HAL_Delay(500)` is now 1 ms; AUTO acquisition
  uses a 250 ms trigger window (NORM/SINGLE keep the 1 s window).
* **P1-3 labels/marker** - the bottom scale uses `timebase_label()` for the selected
  timebase, and the trigger marker uses `acq_trigger_level_get()`.
* **P1-4 persistence integrity** - see P0-1: CRC + version + sequence and alternating
  slots; a corrupted slot is ignored rather than trusted. The calibration record is
  CRC-checked too. (A full multi-record journal is still not implemented; two slots are
  the journal.)
* **P1-5 fastest timebases** - `acq_set_timebase()` rejects `single_shot == 0` entries
  (`ACQ_PARAM`); the menu and the persisted-settings path clamp to indices 5..26.
* **P1-6 stock parity** - not implemented in this pass (measurements beyond Vpp,
  frequency/duty, save/load waveform, average/cycle, clear-offset/defaults, 9-step
  per-sensitivity calibration). This is the next feature phase.
* **P2-2 test coverage** - new/updated suites: `test_crc16`, `test_flash_layout`,
  `test_settings` (codec, corruption, slot order). `acq.c`, `menu.c` and the HAL-level
  modules remain untested on the host.

### 8.1 Re-audit of the remediation (same day)

Two real defects introduced/left by the first remediation pass were found by reading
the changed code again, and fixed:

* **Recovery re-init reset the trigger band and the timebase.** `acq_init()` is called
  again by `acq_bench_poll()` after a hardware error; it wrote the analog-watchdog band
  from the compile-time `ACQ_TRIGGER_LEVEL` and restarted the timer at
  `ACQ_DEFAULT_TIMEBASE`, while `acq_trigger_level_get()`/`acq_timebase_get()` still
  reported the user's values. The marker and the UI therefore disagreed with the
  hardware after a recovery. `acq_init()` now preserves `s_trig_level` and `s_timebase`
  across a re-init and re-arms SINGLE (otherwise the instrument would stay in HOLD
  forever after a recovered fault).
* **Queued menu events had no timestamps.** The tap/double-tap decision was made with
  the time `menu_poll()` ran, but the loop can block for the trigger window (250 ms
  AUTO, 1000 ms NORM/SINGLE). Two independent taps more than 300 ms apart could be
  drained in one poll and misread as a double-tap (net one step back instead of two
  forward). Each queue entry now carries its SysTick timestamp and the double-tap
  window is measured between the events, not between poll iterations.

Remaining findings from the re-audit, deliberately not changed in this pass:

* **Calibration is still inert.** `cal_active` is loaded and editable, but no
  per-sensitivity offset is applied to the trace and the Vpp readout is a raw count
  ratio. CAL-03/CAL-04 remain unmet until a per-range offset table and its application
  point exist.
* `menu_persist()` writes the menu's cached `run`/`stream`, so RUN/STOP/STREAM set over
  the PC link is not persisted and a later menu save can overwrite it with a stale run
  state.
* `cal_store_write()` ignores a flash write failure (the `.noinit` warm copy still holds
  the value until power-off).
* `link_arg_valid()` still advertises timebase indices 0..4, which `acq_set_timebase()`
  now rejects; the reply status is correct but the advertised range is not.
* `SET_SPAN` is overwritten by `ladder_refresh()` every frame (pre-existing).
* Full-frame clear/redraw flicker remains (P2), and there is still no host test for
  `menu.c`, `acq.c` or any HAL-level module.

## 9. Calibration application and link/persistence consistency (2026-11-05, later)

The three items left open in §8.1 that concern calibration and the PC link are now

### 9.1 Per-sensitivity zero table (CAL-03 / CAL-04)

* `app/cal_table.{h,c}` - NEW.  Nine entries, one per front-panel sensitivity combo
  (`range * 3 + gain`), each holding the raw ADC count that represents zero volts for
  that combo, plus a presence mask.  A calibrated zero of 0 counts is legal, so the
  mask - not the value - decides presence; unpacking also drops any entry above 4095
  counts and clears its mask bit rather than mapping the trace to an impossible level.
* `app/cal_store.{h,c}` - record grown to 40 bytes (`CAL2`, version 2, CRC-16/CCITT-FALSE
  over the whole record, base `offset_uv`/`gain_q16`, the packed table, reserved).
  `cal_store_write()` now returns the flash status, so a failed save is retried instead
  of being silently forgotten.  `cal_store_read()` refreshes the `.noinit` warm copy from
  flash, so the base pair and the table can never come from different records.
* `app/menu.c` - new `CAL ZERO` page between `TRIG LEVEL` and `CAL OFFSET`.  A tap
  captures the current frame mean as this combo's zero; the backward (double-tap) path
  clears it.  The strip shows `ZERO c<n> <counts>`, `ZERO c<n> --` when the combo has no
  stored zero, and `ZERO c? --` when the front-panel switches do not decode to a combo.
  A value only marks the record dirty when it actually changed, so holding the button at
  a clamp limit no longer queues a redundant erase.
* `app/main.c` - `scope_draw()` centres the trace on the stored zero for the active
  combo when one exists, and on the frame mean otherwise; `acq_bench_poll()` feeds each
  fresh frame to the menu (`menu_frame_mean()`), but only while not streaming, where the
  combo index would be stale.

Still open, and deliberately so: the base `offset_uv`/`gain_q16` pair is stored,
editable and reloaded, but it does not yet change the volts/div label or the Vpp number
(both stay derived from the front-panel switch decode, which is what makes the label and
the trace agree).  Applying it needs a measured reference to fix the divider ratio, so
CAL-03 stays "partly met" - the per-combo zero is real, the absolute scaling is not.

### 9.2 One source of truth for RUN / STREAM

* `app/runstate.{h,c}` - NEW.  `runstate_run()/runstate_run_set()`,
  `runstate_stream()/runstate_stream_set()`, normalised to 0/1.
* `app/main.c` - the old `static s_run` / `static s_stream` are gone: the PC link
  (`op_run`, `op_stream`, `op_status`), the acquisition gate and the loop delay all use
  the module.
* `app/menu.c` - `menu_persist()` saves `runstate_run()`/`runstate_stream()` instead of a
  cached copy, and `menu_init()` applies the persisted flags through the module.  A
  RUN/STOP/STREAM issued over the link is therefore never overwritten by a stale menu
  value.

### 9.3 Link / decode consistency

* `app/link_cmd.c` rejects `SET_TIMEBASE` below `TIMEBASE_FIRST_SINGLE_SHOT`, matching
  what `acq_set_timebase()` actually accepts (the five equivalent-time-only entries are
  not silently accepted and then ignored).
* `app/main.c` `ladder_refresh()` keeps the previous decode when a channel read fails,
  and only recomputes span/mV-div/range/gain when the decoded switch pair actually
  changed - so a `SET_SPAN` from the host survives until a physical switch moves.

### 9.4 Remote-control path verification

The PC link was re-checked end to end after the calibration work.  The framing,
CRC, parser, dispatcher and streaming path were all intact, but the range policy had
drifted away from the code: `link_cmd_arg_valid()` was only ever called by the unit
tests, so the device did not enforce it.  Three real consequences:

* `SET_TIMEBASE` carries a 16-bit argument but the dispatcher cast it to `uint8_t`
  before calling the engine, so 261 (`0x0105`) wrapped to index 5 and was applied
  with status OK;
* a `SET_TRIGGER` argument above 4095 was silently clamped by the engine and answered
  OK instead of BAD_ARG;
* a `STREAM` argument other than 0/1 was normalised and answered OK.

`link_host_exec()` now validates the argument (for known opcodes) before it calls any
hook and returns `LINK_ST_BAD_ARG` with value 0 for an out-of-range command; unknown
opcodes still return `LINK_ST_UNKNOWN`.  The unit test was updated accordingly, and a
new `tests/test_link_e2e.c` drives the full composition - host encode -> device parse
-> dispatch -> device reply encode -> host parse - for every opcode, including the
wrap case, so a future change in any layer cannot break the chain silently.
`app/main.c` also suppresses the `alive` keepalive while streaming, so the sample
stream no longer carries interleaved ASCII between binary frames.
